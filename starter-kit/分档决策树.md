# 分档决策树

三个问题答完之后，用这棵树决定用哪一档流程开工。**三十秒就该走完。**

```
三个问题都答上来了吗？
│
├─ 没有（第 3 题答不出）─────────→ 先出 DEMO，回 starter-kit
├─ 没有（第 1 题都答不出）───────→ 你要的不是做东西，是想清楚要做什么。先别开窗。
│
└─ 都答上来了
   │
   ├─ 这事几天能做完？
   │  └─ 是 ────────────────────→ 【小型】一页宪法 + DECISIONS + 换窗归档
   │
   ├─ 几周，而且你打算开 3–5 扇窗？
   │  └─ 是 ────────────────────→ 【中型】三个位 + 单机工单台
   │
   └─ 数月，十几条并行的线？
      └─ 是 ────────────────────→ 【大型】四层一席全套
```

## 拿不准的时候往小了选

**升档比降档容易得多。** 升档是加东西；降档要把已经长在流程里的表格拔掉，
而且你会舍不得——毕竟"都建好了"。

小项目上大框架的失败形状很具体：第四天你开始偷偷跳过流程。
而**被偷偷跳过的流程比没有流程更坏**，因为台面上还写着它在跑，
你会照着那张台面做判断。

## 三个不看规模、只看症状的信号

规模只是代理指标。真正该看的是这三条，**任意两条中，就往上走一档**：

1. **你能不能在脑子里记住「现在有哪几件事在办」？** 记不住了 → 至少中型。
2. **有没有出现过「我以为它做完了，其实没有」？** 出现过一次以上 → 至少中型。
   （你需要的是复核，不是更好的模型。）
3. **两扇窗有没有改过同一个文件 / 抬过同一个号？** 有 → 大型。
   （你需要的是并线次序，不是更清楚的分工。）

详细的升降档时机与操作见 [`../frameworks/升降档.md`](../frameworks/升降档.md)。

## 三档各自第一天做什么

### 小型（5 分钟）

```bash
# 照 ../1-小型.md 第一~三节的内容，在项目根建三个文件
```
开窗贴 `宪法.md` 最后那段开窗话术。**完了。**

### 中型（1 小时）

1. 装工单台单机版：[`../ticket-desk/`](../ticket-desk/)，配置三个位。
2. `宪法.md` 用中型那份。
3. **把手上在办的每件事各建一张单**——哪怕做了一半，补一张设成「已认领」。
   ★这一步最容易跳过，跳了之后新旧两套并存两周，然后你会放弃工单台。
4. 开一扇复检窗，让它把已经"做完"的东西重验一遍。
   第一次重验通常会找出一两个问题，那就是这次升档的回本点。

### 大型（半天）

1. **先切位**——按模块切，不按工序切。这是全部重点。
2. 每位写一份章程。
3. 把复检位独立出来：从此它不接受任何人的指挥，**包括你**。
4. 其余（服务端、分发位、三档任务书、模型名册）按需要陆续加。

## 最后

**框架是用来省事的，不是用来证明你在正经做事的。**

任何一条规矩，如果你说不出它防的是哪一次具体的事故，那它多半是抄来的。
删掉试试——三天之内没出事，就是真的不需要它。
