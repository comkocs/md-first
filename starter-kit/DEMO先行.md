# DEMO 先行：用一页假东西把真需求问出来

## 什么时候用

只在一种情况下用：**「什么算做完」这个问题答不出来。**

答不出来不是因为你懒，是因为你脑子里还没有那个画面。
这时候写代码是最贵的探索方式——一天写出来的东西，你看一眼说「不对」，
然后那一天就没了，而且你还得先把它删掉才能重来。

一页 DEMO 半小时，说「不对」的成本是零。

## 三条硬规矩

**1. 单个文件夹，三个文件，双击就开。**
不连后端、不装依赖、不建目录、不用框架。
任何一个「先 npm install 一下」都会让这页 DEMO 迟到两小时，
而它的全部价值就在于**快**。

**2. 只做最核心的那一个画面。**
不做导航、不做设置页、不做登录、不做空状态。
多做的每一样都在把注意力从那一个真问题上引开——
需求方会开始跟你讨论导航栏该放左边还是上边。

**3. 做完就扔。**
DEMO 是提问工具，不是原型，更不是代码基础。
在 DEMO 上继续长功能的代价会一直跟着你：那些为了"先看看效果"写死的假数据结构，
会变成真的数据结构，然后你会在三个月后还在绕着它写代码。

## 假数据要假得像真的

这条最容易被做反。

| 不好 | 好 |
|---|---|
| 测试用户 1 / 测试用户 2 | 张三 / 李四 |
| 123.00 | ¥2,400（房租） |
| item-1, item-2, item-3 | 房租 / 菜市场 / 地铁月卡 |
| Lorem ipsum | 真的中文句子，长度也像真的 |

**假得太明显的数据不会让人产生意见。** 而产生意见正是这页 DEMO 的全部目的。
看见「测试用户 1」，人只会说「嗯，知道了」；
看见「朋友生日礼物 ¥260」，人会说「诶这个应该算在'其他'还是单独一类？」——
**后面那句话就是你要的东西。**

同理：数据条数也要像真的。三条看不出问题，三十条才会暴露"这个列表太长了得能搜"。

## 只问一句

给出 DEMO 之后，**只说一句话**：

> 你点一下，哪里不对？

不要问「你觉得怎么样」（会得到「挺好的」），
不要问「还需要什么功能」（会得到一张许愿单），
不要自己先解释你做了什么（会把他的注意力引到你想让他看的地方）。

「哪里不对」这个问法假设了一定有不对的地方，所以人会真的去找。

## 一轮 DEMO 之后

把听到的每一句「不对，这里应该是……」记下来，然后回去答那个问题：

```
什么算做完？—— 我 <点哪里/跑哪条命令>，看见 <什么>，就算做完了。
```

这时候通常答得出来了。答不出来就再改一版 DEMO——**但最多两版**。
两版之后还答不出来，说明问题不在画面上，在你还没想清楚要解决什么问题，
那是另一件事，不是 DEMO 能解决的。

## 骨架怎么用

[`demo-template/`](demo-template/) 里三个文件，双击 `index.html` 就能看。

改法：**只改 `demo.js` 顶部的 `DATA`，和 `index.html` 里那三块的文字。**
渲染代码不用动。

骨架给了三块，因为几乎所有东西都是这三块的组合：

1. **最重要的那个数 / 那句话** —— 打开第一眼看见的东西
2. **一张清单** —— 多数东西的主体都是这个形状
3. **一个能点的动作** —— 多数「不对」都在这里被说出来

用不上的那块就删掉，别留空着——空着的区域会引来关于"这里放什么"的讨论。

## 给 AI 窗口的话

要让一扇窗替你出 DEMO，贴这段：

```
给我出一页可以点的 DEMO，用来帮我想清楚需求。规则：
· 单个文件夹三个文件（index.html / demo.js / demo.css），纯静态，双击能开；
· 不连后端、不装依赖、不建目录、不用框架；
· 只做 <一句话说清那个核心画面>，不做导航、不做设置、不做登录；
· 假数据要像真的（真名字、真金额、真长度），条数给够（十条以上）；
· 做完只问我一句：「你点一下，哪里不对？」不要解释你做了什么。

★这是一次性的提问工具，不是原型。不要在它上面继续长功能。
```
